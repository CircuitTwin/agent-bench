# agent-bench

A benchmark for firmware emulators: do they catch the bugs that coding agents commonly write into STM32F4 firmware,
and do they leave correct firmware alone?

It holds 17 small tasks for an STM32F407 board (drive a GPIO pin, count timer interrupts, copy memory by DMA, address
an I2C sensor that is not on the bus, ...). Each task has a correct firmware (`v0`) and one to four buggy versions, each
with a bug of a kind agents commonly write: a peripheral clock never enabled, an interrupt flag never cleared, an
unbounded poll on a flag that never sets, a wrong register field, ... In total **43 firmware images, 26 of them buggy**.
Every image is built once and runs unchanged on two platforms:

* **CircuitTwin**: `ct run <elf> --board stm32f4-discovery`, the digital twin of the STM32F4DISCOVERY board;
* **QEMU** 10.0.13, machine `olimex-stm32-h405`, from a pinned container image.

The scorer counts, per platform, the buggy versions it **catches**, the ones it **misses**, and the correct versions it
wrongly **flags** (false alarms). The tasks were written for this benchmark; they are not a survey of real agent output.
The results are provisional: "caught" means the emulator showed the failure, not that silicon was compared.

## Published numbers

Recorded on 2026-11-21 with the pinned `ct` build (below), from a clean source tree, all 43 images on both platforms.
The record is [`results/2026-11-21/`](results/2026-11-21): `report.md` has every case, `summary.json` the same as data,
`results.json` and `raw/` are what the runner wrote.

| platform | buggy versions | caught | missed | correct versions | false alarms | caught and different from the correct version | caught by a platform signal |
|---|---|---|---|---|---|---|---|
| CircuitTwin | 26 | 24 | 2 | 17 | 0 | 24 | 16 |
| QEMU | 26 | 20 | 6 | 17 | 7 | 8 | 5 |

Caught by both: 19. CircuitTwin only: 5 (`baud` v1, `clk_timer` v1, `irq_chain` v3, `race` v1, `wdg` v1). QEMU only: 1
(`i2c_nack` v2). Neither: 1 (`reset_vals` v1).

* **Missed by CircuitTwin:** `i2c_nack` v2 (a bounded wait that never checks the NACK: the twin cannot tell it from the
  correct version once the NACK of an absent address is only informational) and `reset_vals` v1 (SRAM reads 0 in the
  default run; with `--uninitialized-memory seeded:1` the firmware's own check catches it, see "Twin with a non-default
  option" in the report).
* **Missed by QEMU:** `baud` v1, `clk_timer` v1, `irq_chain` v3, `race` v1, `reset_vals` v1, `wdg` v1.
* **False alarms:** none on CircuitTwin. QEMU flags the correct `clk_gpio`, `dma_m2m`, `gpio_mode`, `i2c_nack`, `pll`,
  `psc` and `ro_write`: on each, the firmware's own self-check printed FAIL, because the peripheral or the clock tree it
  reads back is not modelled by QEMU's STM32F405 machine (the report lists the unimplemented-device lines QEMU logged for
  every image).

How the columns are computed (`tools/report.py`, from the raw records only):

* *caught*: the run is not a clean pass. Signals: `self-check` (the firmware printed FAIL), `hang` (no result line before
  the limit), `fault` (CircuitTwin stopped at a fault; QEMU logged a UsageFault, BusFault or HardFault), `twin-diagnostic`
  (CircuitTwin reported an issue, a verdict note, or a verdict other than pass).
* *missed*: a buggy version that looks like a clean pass. *False alarm*: a correct version that is flagged.
* *caught and different from the correct version*: the signal differs from what the correct version of the same task
  produced on that platform; a catch identical to the correct version's flag says nothing about the bug.
* *caught by a platform signal*: at least one signal other than the firmware's own FAIL line.
* A twin run that reaches `--until` has the verdict `pass` even when the firmware printed FAIL, so the console text is
  part of the classification. QEMU `unimplemented device` log lines are listed as information; they do not count as a
  catch. Informational twin issues (such as the NACK of an absent address) are listed but are not a diagnostic.

## What the tasks are

`cases.json` lists every task, version and bug (the bug class and a one-line description), `firmware/src/<case>.c` is the
source (one file per task, the bug selected by `-DBUG=N`), `firmware/src/rt.c` and `rt.h` the shared runtime. Every image
prints `CT-BENCH <case>_v<N> PASS|FAIL <message>` and then `CT-BENCH-DONE` on USART2.

| task | what the firmware does | bugs |
|---|---|---|
| `clk_gpio` | drive PD12 high and read it back | GPIOD clock never enabled |
| `clk_timer` | start TIM3 and see its counter advance | TIM3 clock never enabled |
| `gpio_mode` | configure PD12 as output, drive it high, read the pin level | MODER written at the pin number instead of twice the pin number |
| `poll_flag` | send a byte and wait for transmit complete | unbounded poll on RXNE, which never sets |
| `irq_chain` | count three TIM3 update interrupts | NVIC enable forgotten; DIER.UIE forgotten; flag never cleared; handler name misspelled |
| `nvic_prio` | a TIM3 handler waits for a SysTick tick, which must preempt it | TIM3 at the same priority as SysTick: no preemption |
| `dma_m2m` | DMA2 stream 0 memory-to-memory copy of 16 words | DMA2 clock never enabled; FIFO direct mode left on; NDTR left at 0 |
| `wdg` | 200 ms of work under a 31 ms independent watchdog | the watchdog is never kicked |
| `baud` | report the result at 115200 baud | BRR computed for an unconfigured 42 MHz APB1 |
| `i2c_nack` | address a sensor that is absent from the bus | unbounded wait for ADDR; bounded wait that never checks AF |
| `reset_vals` | use a never-written SRAM word | assumes SRAM reads 0 at power-up |
| `stack` | recursive sum | depth that outruns the 128 KB of SRAM |
| `unaligned` | read a 64-bit pair from a byte buffer | LDRD at an address 2 mod 8; unaligned word load with UNALIGN_TRP set |
| `race` | read an ISR-published pair (a, ~a) from main | two-word read without masking interrupts |
| `psc` | TIM3 at 1 MHz from 16 MHz HSI, cross-checked with SysTick | PSC off by one (divide by 17) |
| `ro_write` | drive PD12 high (or store a flash word) and read it back | writes the read-only IDR; stores to flash without unlocking it |
| `pll` | switch to the 168 MHz PLL, verify, return to HSI | flash wait states never set; SW and SWS used without waiting for PLLRDY |

## Reproduce

> **The pinned `ct` and `ct-server` builds are not publicly downloadable yet.** Steps 1 to 3 below need neither of them.
> Reproduction of the full record (steps 4 to 6) is available on request: open an issue on this repository
> (<https://gitlab.com/apanter265/agent-bench/-/issues>) and say that you want to reproduce the record.

### What you need

| | |
|---|---|
| Python 3.9 or newer | every tool in `tools/` (standard library only) |
| Docker, Linux containers | builds the firmware toolchain image (about 2.7 GB) and the QEMU image from the Dockerfiles in this repository, and runs them (the tools never run an image that is not built locally). The first build downloads the pinned base images and Debian packages (Docker Hub, `snapshot.debian.org`). |
| git | to clone this repository |
| the pinned `ct` release | `ct 0.1.0`, Windows x86_64: `ct.exe` (sha256 `3c5ab24e7a1cf3a8ee5519f3cddaf0ba90af1d7a4c30b65337ba121a80d598d4`) and `ct-server.exe` (sha256 `36f2d30e25b16656af8ea89b3034ccde4da67509f00be27b5531c3a5c4fae464`), from `ct-release.json`; not publicly downloadable yet, see the note above. Check them before use: `sha256sum ct.exe ct-server.exe`, or `Get-FileHash ct.exe, ct-server.exe` in PowerShell. |
| the twin's documents | four files, laid out as in [The twin](#the-twin) |

The runner records whether the `ct` it was given is the pinned build (`ct.pinned` in `results.json`, and a line in the
report). With another build, or another operating system, the benchmark still runs, but its numbers are not those of the
published record.

### Steps

Run everything from the root of a fresh clone.

```text
git clone https://gitlab.com/apanter265/agent-bench.git
cd agent-bench
git checkout v2026.11.21
```

**1. Re-score the published record** (no `ct`, no Docker). This only runs the scorer on the committed raw records:

```text
python tools/report.py --out results/2026-11-21 --against results/2026-11-21
```

It writes `report.md` and `summary.json` next to the record (identical to the committed ones) and prints
`identical to results/2026-11-21: totals and 43 cases (88 platform results: ...)`.

**2. Build the firmware** (in a container; the first run also builds the toolchain image, which takes several minutes):

```text
python tools/build-firmware.py --out build/fw --expect results/2026-11-21/firmware-build.json
```

It writes 43 ELFs and `build/fw/firmware-build.json`, and ends with
`identical to results/2026-11-21/firmware-build.json: all 43 images are byte-identical`.

**3. Build the QEMU image:**

```text
docker build -t agent-bench/qemu-system-arm:10.0.13-1 qemu
```

`tools/run.py` refuses an image whose `/usr/bin/qemu-system-arm` is not the one pinned in
`qemu/qemu-system-arm.lock.json`.

**4. Start a server for `ct`.** Every `ct` command needs a signed-in CircuitTwin account. For the record that was a local
server of the pinned release, with development sign-in (loopback only; any well-formed e-mail address signs in). In a separate
terminal, and leave it running:

```text
python tools/local-server.py --server-bin <dir with the pinned release>/ct-server.exe
```

It starts the server on `http://127.0.0.1:8137`, creates an account and an access token (scope `twins`), writes the token
to `work/token.txt` (mode 600 where the system has file modes; it is never printed) and keeps running until Ctrl-C. To use
a hosted server instead, create an access token in the web app (Settings, Access tokens) and pass `--server <url>` and
`--token-file` to `tools/run.py` below, or run `ct login --server <url>` once and pass neither; that setup was not used for
the record.

**5. Run both platforms.** Point `ct` at the documents of the twin (laid out as in [The twin](#the-twin)) and at a fresh
catalog, so the first run builds the twin and prints its id. In bash:

```text
export CT_SOURCES_DIR=<inputs>/sources
export CT_DATASHEET_CORPUS=<inputs>/vendor
python tools/run.py --ct <dir with the pinned release>/ct.exe --server http://127.0.0.1:8137 --token-file work/token.txt \
    --fw build/fw --catalog-dir work/catalog --out out/run
```

In PowerShell, set the two variables with `$env:CT_SOURCES_DIR = '<inputs>\sources'` and
`$env:CT_DATASHEET_CORPUS = '<inputs>\vendor'` and put the `run.py` command on one line. It runs the 43 images on `ct`
(45 runs: `reset_vals` also runs with `--uninitialized-memory seeded:1`) and on QEMU, takes about six minutes on an otherwise
idle machine, and writes `out/run/results.json` and one file per run in `out/run/raw/`. A `ct` run that produces no
verdict (sign-in refused, server not reachable) is listed at the end with its reason and makes `run.py` exit with 1; the
report flags such runs too.

**6. Score and compare:**

```text
python tools/report.py --out out/run --against results/2026-11-21
```

It writes `out/run/report.md` and `out/run/summary.json`, and compares the totals and every case on every platform
(caught flag, signals and evidence text) with the published record. A reproduction ends with
`identical to results/2026-11-21: totals and 43 cases (88 platform results: ...)`; any difference is listed and the exit
code is 1.

`run.py --skip-twin` or `--skip-qemu` runs one side, `--only <case,...>` some tasks; results merge into `results.json`.

### The twin

`ct run --board stm32f4-discovery` needs the STM32F407VG twin in its local catalog (`CT_CATALOG_DIR`) or in the catalog of
the server you are signed in to. `ct board list --local --json` shows where each board's twin can come from and which
inputs are found. The record's twin was generated by `ct` on its first run from the four documents below; the run prints
`ct run: generated the STM32F407VG twin twin:1a1b7140c278c3f0 from STM32F407.svd + zephyr.dts + rm0090-stm32f4-series-reference-manual-stmicroelectronics.pdf + stm32f407v-e-g-tx-pinctrl.dtsi into the catalog at ...`.
Lay them out like this (`<inputs>` is any directory; the documents are not part of this repository):

| document | path | sha256 |
|---|---|---|
| `STM32F407.svd`, the CMSIS-SVD description of the part (device version 1.2) | `<inputs>/sources/test-firmware/svd/STM32F407.svd` | `2ae448095ec929272bcde4ae4b854b654e20d4ea107d80dcffcf806dcc69369d` |
| `zephyr.dts`, the flattened devicetree of Zephyr's `stm32f4_disco` board (Zephyr commit `36940db938a8f4a1e919496793ed439850a221c2`, a `hello_world` build) | `<inputs>/sources/test-firmware/boards/stm32f4-discovery/zephyr.dts` | `0f37565e6bd9e3cd037b1602fbab997d1c35d79082f0f60e2bdb7ab8c1a2edaf` |
| RM0090 Rev 22, ST's reference manual of the STM32F405/407/415/417/427/437/429/439 | `<inputs>/vendor/mcu/stm32f407vg/rm0090-stm32f4-series-reference-manual-stmicroelectronics.pdf` | `f3ff2322eec21f4e49081f68481b764506eee81dba6031bc767e2f8955b27cca` |
| `stm32f407v-e-g-tx-pinctrl.dtsi`, the pin-control include of Zephyr's `hal_stm32` module (Apache-2.0) | `<inputs>/vendor/mcu/stm32f407vg/stm32f407v-e-g-tx-pinctrl.dtsi` | `10187931fcd169e45d741f8c0ca134b00e777d9d33e3de33bc89f5f5712c2239` |

The SVD and the manual are ST's; check the digest of every file you use. Two things change the twin you get:

* **Other inputs.** Without the last two files `ct` builds another twin (`twin:ec1299ce48246a84` when tried), and a server
  whose catalog already holds a twin of the part gives `ct run` that twin instead. In a test with both variables unset, `ct`
  still generated a twin, from the SVD and the devicetree only (`twin:ec1299ce48246a84`), and the runs completed.
* **The order of the files.** In the layouts tried, `ct` listed the documents in the order of their sorted absolute paths,
  and the twin's id covers that order. With `sources` sorting before `vendor`, as above, the id is the record's. With the
  directories the other way round (for example `corpus` and `sources`) the id is another one (`twin:e2cd0fe6aedf9810` when
  tried). Apart from provenance records (the order of the listed documents and which document some pin-mux citations
  name), the two twins are identical.

`tools/report.py` compares the id of the twin the runs generated with the record's (`twin.id` in `ct-release.json`): its
`twin` row says whether it is the record's twin, and it warns when it is not. Compare the id before comparing numbers.

How a run is made:

* **CircuitTwin:** `ct --json run <elf> --board stm32f4-discovery --max-ms N --until CT-BENCH-DONE --console-baud 115200`
  (`N` is 500 ms, 1000 ms for the interrupt tasks and 600 ms for `wdg`; default `--unmodelled behavioural`).
  `--console-baud` declares the rate the console peer expects; without it nothing is compared and `baud` v1 passes.
* **QEMU:** `qemu-system-arm -M olimex-stm32-h405 -kernel <elf> -display none -monitor none -serial null -serial file:...
  -icount shift=2,sleep=off -d guest_errors,unimp,int`, USART2 on a file, stopped at `CT-BENCH-DONE` or after 4 s of wall
  time (`qemu/run.sh`). Virtual time is deterministic, the wall limit is not: on a loaded host QEMU can need seconds just to
  start. `tools/run.py` therefore repeats a run that reaches the limit once, with 20 s, and records a hang only for a run
  that stops again; a run that finishes in the repeat is recorded as finished and the host is reported as loaded. The
  published record was made with the single 4 s attempt. Its five hangs (`irq_chain` v4, `poll_flag` v1, `stack` v1,
  `unaligned` v1 and v2) do not finish within 60 s either.
* **Firmware:** `-O1`, soft-float, no libc and no vendor library (register addresses only), Cortex-M4, the linker script
  of an STM32F407VG (1 MB flash, 128 KB SRAM at 0x20000000). The same ELF runs on both platforms.

## Target mismatches

* CircuitTwin: STM32F407VG (128 KB SRAM at 0x20000000 as the linker script uses it, 1 MB flash), HSI 16 MHz at reset,
  HSE 8 MHz on the board. QEMU: the STM32F405 SoC on the Olimex STM32-H405 (192 KB SRAM). The two parts share the memory
  map for everything the tasks touch. QEMU has no STM32F407 machine; `netduino2` is an STM32F205 (Cortex-M3) and was not
  used.
* QEMU 10.0.13 models only part of the SoC. In the record its log names GPIOA, GPIOB, GPIOD, DMA2, I2C1 and an I2S2ext
  window as unimplemented devices: a correct version that reads a flag back from one of them cannot pass there
  (`clk_gpio`, `gpio_mode`, `ro_write`, `dma_m2m`, `i2c_nack`). The correct `pll` fails on QEMU at `HSE not ready` (the
  flag never reads back) and the correct `psc` because QEMU's timer clock does not follow the 16 MHz HSI the task
  assumes. CircuitTwin models those peripherals and clocks, or reports the access.
* QEMU ignores the UART baud rate (the line is a byte stream), so `baud` is invisible to it; CircuitTwin flags it only when
  the peer rate is declared (`--console-baud`).
* Time is virtual on both sides, but not the same virtual time: interrupt timing tasks (`race`) depend on how each engine
  delivers an interrupt between two instructions.

## How the record came about

The tasks were written by the CircuitTwin team, and the first run (2026-11-20) was also used to find gaps in the twin, so
the numbers above are those of a twin that was improved after it had run this benchmark. That run missed `baud` v1,
`dma_m2m` v2, `reset_vals` v1 and `wdg` v1 and flagged the correct `i2c_nack`. Each was traced:

| task | first run | cause | change |
|---|---|---|---|
| `baud` v1 | missed | the console had no declared peer rate | `ct run --console-baud`: a UART whose programmed format differs from 8N1 at that rate raises `bus.serial.baud-mismatch`. The benchmark passes `--console-baud 115200` (`twinArgs` in `cases.json`). |
| `dma_m2m` v2 | missed | the model ran direct mode in memory-to-memory without comment | RM0090 DMA_SxFCR.DMDIS: hardware sets DMDIS when DIR=10 and EN=1, so the stream runs through the FIFO and reports `peripheral.config.invalid`. The copy still completes, as the manual describes, so the self-check passes. |
| `reset_vals` v1 | missed (`seeded:1` refused) | no recorded rule for the part | rules for STM32F4 (RM0090), F1 (RM0008) and F0 (RM0091): SRAM contents are lost in Standby, deterministic per seed. With `seeded:1` the check fails (caught); the default run still reads 0. |
| `wdg` v1 | missed | the firmware: it reloaded before the start key, so the counter stayed at 0xFFF | `wdg.c` follows the order of the manual: start key, unlock, PR, RLR, wait for IWDG_SR = 0, reload. The watchdog model was right. |
| `i2c_nack` v0 | false alarm | an absent-address NACK was a warning | it is an informational issue, listed but not counted as a diagnostic. `i2c_nack` v2 is now missed, because the twin cannot tell a NACK nobody checks from one handled. |

The `--console-baud` check also showed that the correct `pll` returned to HSI but left the APB prescalers at /4, so its
console would run at 28.8 kbaud on silicon too; `pll.c` now restores them. All of this is provisional; none of it was
checked against silicon.

## Limits

* The self-checks are written by the benchmark author. Some bugs have no effect the firmware can test on its own:
  `baud` v1 sends its bytes, `reset_vals` v1 reads 0 in the default run, and `wdg` v1 only prints FAIL if the platform
  really resets on the watchdog. Those can be caught only by a platform signal: CircuitTwin gives one for `baud` (with
  `--console-baud`) and `wdg`, and for `reset_vals` only under `--uninitialized-memory seeded:1`; QEMU gives none.
* One version per bug shape, 26 buggy versions in 16 classes: the counts are not rates and carry no confidence interval.
* `race` is probabilistic in nature; both results are the single deterministic run of each engine.
* No hardware reference was run: "caught" means the emulator showed the failure, not that silicon was compared.
* The pinned build and the record are for Windows x86_64.
